# Інструкції для Claude Code

## Референси й проєктна документація

У `reference/` зберігаються приклади для ознайомлення, а не кодова база цього фреймворку:

- `reference/playwright-test-automation-template/` — приклад структури Playwright + TypeScript: UI/API/E2E тести, fixtures, Page Objects, компоненти, моделі, сервіси, фабрики даних і `storageState`. Ліцензія — MIT.
- `reference/design-patterns-typescript/` — навчальні приклади GoF-патернів на TypeScript. Це не Playwright-фреймворк. Ліцензія — CC BY-NC-ND 4.0.
- `.claude/skills/playwright-best-practices/SKILL.md` — додатковий довідник із локаторів, перевірок, очікувань, структури тестів і мокування API, взятий із [GenAIEventHub](https://github.com/RomanMakarenko/GenAIEventHub/blob/claude/eventhub-updates/.claude/skills/playwright-best-practices/SKILL.md). Це рекомендації з іншого проєкту, не джерело конфігурації для цього фреймворку.
- `playwright-mcp-context.md` — докладні правила та workflow для браузерної роботи й тестів у цьому репозиторії. Він доповнює, але не замінює `CLAUDE.md`, конфігурацію та фактичний код.
- `.claude/skills/playwright-cli/SKILL.md` і файли в `references/` поруч — довідник для опційного `playwright-cli`: браузерні сесії, Playwright-тести, мокування запитів, traces, відео та інші спеціалізовані задачі. Застосовуй його для відповідних задач, але звіряй приклади з поточною конфігурацією проєкту.
- `docs/IMPLEMENTATION_PLAN.md` — дорожня карта та єдине джерело чеклістів фаз і статусу їх виконання. Позначай фазу завершеною лише після проходження всіх її критеріїв приймання.
- `docs/RUNBOOK.md` — хронологічний журнал значущих checkpoint-ів: виконана робота, причина, перевірки та handoff. Це історія змін, не поточний статус реалізації.
- `docs/DECISIONS.md` — журнал довготривалих архітектурних і процесних рішень зі стабільними ID, обґрунтуванням та наслідками.

## Ведення проєктних записів

- Після значущої задачі, milestone або handoff додавай запис у `docs/RUNBOOK.md`: дату, scope, змінені артефакти, причину, точні команди та їхні результати (`PASS`, `FAIL` або `NOT RUN` із причиною), блокери й наступні кроки. Не створюй checkpoint для кожної дрібної правки.
- Записуй у `docs/DECISIONS.md` лише довготривалі рішення, що впливають на архітектуру чи процес. Використовуй наступний стабільний ID і фіксуй контекст, рішення, причину, наслідки та докази; не вигадуй альтернативи, які фактично не розглядалися.
- Оновлюй статус фаз і критеріїв лише в `docs/IMPLEMENTATION_PLAN.md`, і лише після їх перевірки. Не дублюй чеклісти завершення фаз у RUNBOOK чи DECISIONS; за потреби посилайся між документами.
- Вважай RUNBOOK і DECISIONS append-only: не переписуй минулі результати непомітно; виправлення додавай окремим датованим записом. Не записуй у них секрети, credentials, токени чи auth state.

## Поточна структура

- Повторно використовуваний код фреймворку: `src/` (`api/`, `components/`, `config/`, `data/`, `fixtures/`, `models/`, `pages/`, `utils/`).
- Тестові набори: `tests/` (`api/`, `db/`, `e2e/`, `integration/`, `testdata/`, `visual/`), а також наявні приклади тестів.
- `src/utils/` містить реалізовані утиліти для тестових даних, файлів, БД, очікувань UI та дат.
- Кореневі `api/endpoints/` і `api/schemas/` є scaffold-каталогами. Для нового повторно використовуваного коду дотримуйся правила `src/`; не створюй дві копії API-клієнтів або схем у `api/` та `src/api/`. Якщо задача явно вимагає кореневий `api/`, дотримуйся її та поясни розміщення.
- `tests/testdata/` призначений для статичних тестових файлів; не плутай його з повторно використовуваними даними й моделями у `src/data/`.
- Перевіряй фактичний вміст директорій перед використанням: scaffold або план не означає, що там уже є реалізація.

## Стек і конфігурація

- Проєкт використовує npm, CommonJS (`"type": "commonjs"`) і `@playwright/test`. Зберігай сумісність TypeScript, ESLint та Playwright із чинним форматом модулів; змінюй його лише як окреме обґрунтоване та перевірене рішення.
- `tsconfig.json` налаштований на strict type-checking, `Node16` module/moduleResolution та `noEmit`; включає `playwright.config.ts`, `src/**/*.ts` і `tests/**/*.ts`, виключає `reference/` і згенеровані результати. Не додавай alias-імпорти, яких немає в конфігурації.
- `playwright.config.ts` є джерелом істини для запуску: `testDir: './tests'`, проєкти Chromium, Firefox і WebKit, HTML reporter, `trace: 'on-first-retry'`, CI retries/workers. `baseURL`, автоматичне завантаження dotenv та `webServer` зараз закоментовані — не припускай, що вони налаштовані.
- У `package.json` наразі немає npm scripts; `typescript` оголошений як `devDependency`. Не вигадуй команди `npm test` чи `npm run typecheck`; перевір актуальні scripts перед використанням. Для типізації використовуй `npx tsc --noEmit`, а для тестів і lint — наявні CLI-залежності, наприклад `npx playwright test`, `npx playwright test --list` і `npx eslint <шляхи>`.
- `playwright-cli` — окремий опційний інструмент браузерної автоматизації, а не залежність `package.json` і не заміна Playwright Test. Не припускай, що він установлений; skill і його references у `.claude/skills/playwright-cli/` є документацією репозиторію.
- Перевіряй фактичні залежності у `package.json`/lock-файлі. Наявність пакета не означає, що його вже підключено до конфігурації або тестів; не додавай залежності без потреби.
- CI workflow у `.github/workflows/` встановлює npm-залежності, браузери Playwright, запускає тести й зберігає HTML-звіт як artifact. Зміни в командах, версіях Playwright або reporter узгоджуй із CI; не додавай секрети до workflow-логів чи artifacts.
- Кореневого Dockerfile/Compose-оточення наразі немає. Коли Docker буде додано, узгоджуй офіційний Playwright-образ із Playwright у кореневому lock-файлі; зберігай результати тестів доступними поза контейнером і передавай секрети лише під час запуску. Не додавай credentials або `storageState` до образу, репозиторію, логів чи artifacts.

## Домовленості щодо реалізації

- Будуй тести на нативній моделі Playwright Test: використовуй типізовані fixtures через `test.extend`, а де можливо — вбудовані `page`, `context` і `request`. За замовчуванням зберігай ізоляцію на рівні тесту; worker-scoped fixtures застосовуй лише для свідомо спільного й безпечного стану. Не перенось Java/TestNG lifecycle, DI чи thread-local driver patterns.
- Застосовуй Page Objects у `src/pages/` для сторінок із повторюваною поведінкою, а компоненти — у `src/components/` лише коли абстракція справді повторно використовується. Не створюй обгортки заради обгорток.
- Розподіляй перевірки за призначенням: UI journey — `tests/e2e/`, API — `tests/api/`, БД — `tests/db/`, взаємодія шарів — `tests/integration/`, візуальні/snapshot-перевірки — `tests/visual/`. Не дублюй одну й ту саму перевірку в кількох шарах без причини.
- Для UI використовуй стійкі доступні локатори (`getByRole`, `getByLabel`, `getByText`) і web-first assertions. Не використовуй довільні sleep/timeout як синхронізацію; дочікуйся конкретного стану чи події.
- Для API за замовчуванням використовуй Playwright `request` fixture або `APIRequestContext`. TypeScript-типи не є runtime-валідацією; для перевірки схем використовуй уже встановлений валідатор лише коли це потрібно контракту.
- Для тестів БД застосовуй наявний `src/utils/dbClient.ts` лише за наявності підтвердженої тестової БД, схеми й безпечного способу очищення даних. SQL-параметри передавай окремо, не конкатенуй їх із запитом.
- Обмежуй зміни задачею. Спочатку шукай чинні fixtures, моделі, API-код та утиліти; не додавай дублікати й не змінюй незв'язані файли.

## Наявні утиліти

Перед написанням нової утиліти перевір відповідний файл і поточні exports у `src/utils/`:

- `dataGenerator.ts`: `generateRandomUser()`, `generateUniqueEmail()`, `generateRandomString()`.
- `DataReader.ts`: `readJsonFile<T>()`, `getEnvVariable()`.
- `dbClient.ts`: `executeQuery<T>()`, `closeConnection()`; MySQL pool створюється ліниво.
- `helper.ts`: `waitForElementToDisappear()`, `parseCustomDate()`, `uploadTestFile()`.

`readJsonFile<T>()` дає лише compile-time типізацію; якщо коректність залежить від структури недовіреного JSON, додай runtime-валідацію. `getEnvVariable()` читає вже наявний `process.env`, але не завантажує `.env` самостійно.

## Захист секретів і змінних середовища

- Не відкривай, не друкуй, не шукай і не намагайся іншим способом прочитати кореневий `.env`. Не обходь Claude Code deny rule або hook.
- Для назв потрібних змінних користуйся `.env.example`; не вважай його значення фактичними локальними секретами.
- Не виводь значення environment variables, паролі, токени, connection strings або auth state у термінал, логи, звіти, скриншоти, traces чи artifacts. Не додавай реальні облікові дані або `storageState` до репозиторію.
- `.playwright-cli/` ігнорується Git, але його snapshots, traces, скриншоти, відео та збережений стан браузера можуть містити чутливу інформацію. Не переглядай і не поширюй такі дані без потреби задачі; перед передаванням будь-кому перевіряй артефакти на секрети.
- `.claude/settings.json` містить deny rule і `PreToolUse` hook для звичайних Claude Code звернень до `.env`. Це захист рівня інструментів, а не OS-level sandbox чи абсолютна ізоляція; не заявляй, що він блокує всі можливі способи доступу.
- У `playwright.config.ts` dotenv-завантаження наразі закоментоване. Не вмикай його та не запускай код, який читає локальні секрети, без чіткої потреби задачі й дозволу користувача. Віддавай перевагу змінним, явно переданим тестовому процесу або CI.

## Як використовувати референси та перевіряти результат

1. Спершу перевіряй структуру, залежності, конфігурацію та домовленості **цього проєкту**; для актуального стану довіряй фактичним файлам, а не планам чи референсам.
2. Використовуй Playwright-шаблон лише для конкретних прикладів ідей; переглядай тільки файли, потрібні поточній задачі. Адаптуй рішення до цього проєкту й не змінюй файли в `reference/`.
3. Для актуальної поведінки й API Playwright орієнтуйся насамперед на офіційну документацію: <https://playwright.dev/docs/intro>. Перед використанням прикладу звіряй його з версіями залежностей і конфігурацією цього репозиторію.
4. Застосовуй із `playwright-best-practices/SKILL.md` лише загальні рекомендації, якщо вони відповідають цьому проєкту. Не перенось специфічні для EventHub URL, селектори чи облікові дані; адаптуй JavaScript-приклади до TypeScript і локальної конфігурації. Вихідний репозиторій не декларує ліцензію — не копіюй і не поширюй його вміст поза локальним референсом без перевірки прав.
5. Не перенось код із `design-patterns-typescript` без окремої перевірки прав: CC BY-NC-ND 4.0 обмежує комерційне використання та поширення похідних матеріалів. Якщо використовуєш код із MIT-шаблону, зберігай відповідне повідомлення про авторські права та ліцензію.
6. Не встановлюй залежності й не запускай тести референсів як частину кореневого проєкту; `reference/` виключений із ESLint та TypeScript compilation.
7. Перед завершенням запускай лише релевантні перевірки, виправляй проблеми, внесені змінами, і звітуй фактичні команди та результати. Якщо перевірку не вдалося запустити, вкажи причину; не стверджуй, що вона пройшла.
