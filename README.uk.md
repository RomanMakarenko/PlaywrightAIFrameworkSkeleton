# Playwright + TypeScript Test Framework Skeleton

Стартовий каркас для UI, API, end-to-end та інших автоматизованих перевірок на **Playwright Test** і **TypeScript**. Репозиторій містить базову структуру, конфігурацію, приклад тесту й утиліти; він не містить окремого застосунку під тестом.

**Мова:** українська · [English](README.md)

## Передумови

- Node.js (рекомендовано актуальну LTS-версію) та npm.
- Доступ до інтернету для встановлення браузерів і запуску read-only E2E та HTTP-перевірок Funtime.

## Встановлення

У корені репозиторію виконай:

```bash
npm ci
npx playwright install
```

На Linux, якщо системні залежності браузерів ще не встановлені:

```bash
npx playwright install --with-deps
```

## Запуск тестів

```bash
# Усі тести в усіх налаштованих браузерах
npm test

# Перелік знайдених тестів
npm run test:list

# Швидка read-only HTTP-перевірка в Chromium
npm run test:smoke

# Один браузерний проєкт
npm test -- --project=chromium

# Інтерактивний режим Playwright
npx playwright test --ui
```

E2E-набір містить read-only сценарії публічного сайту Funtime та HTTP-перевірку доступності; локальний вебсервер не потрібен. `baseURL` Playwright за замовчуванням — `https://funtime.com.ua`; його можна перевизначити через `FUNTIME_BASE_URL`.

## Авторизовані й публічні тести

Тести, яким потрібен вхід у систему, та публічні тести запускаються в **окремих ізольованих контекстах браузера**. Неавторизований тест не успадковує cookies чи інший стан від авторизованого тесту. У Playwright це організовано проєктами:

- `chromium`, `firefox`, `webkit` — звичайні тести. Кожен тест починає з чистого контексту без `storageState`; сюди входять публічні сценарії.
- `auth-setup` — умовний підготовчий проєкт у Chromium: входить під тестовим користувачем і зберігає `storageState`.
- `authenticated-chromium` — умовний проєкт у Chromium: залежить від `auth-setup` і завантажує збережений стан, щоб перевіряти захищені сторінки.

Отже, для повного запуску достатньо виконати `npm test`. Якщо в тестовому процесі присутні **обидві** змінні `APP_EMAIL` і `APP_PASSWORD`, один запуск виконає публічні тести у звичайних проєктах і додатково авторизовані тести в `authenticated-chromium`. Якщо обидві змінні відсутні — авторизований проєкт не додається, а перевірка реального входу `AUTH-002` пропускається. Якщо задано лише одну змінну — це помилка конфігурації.

```bash
# Повний набір: публічні браузерні проєкти + авторизований Chromium,
# якщо APP_EMAIL і APP_PASSWORD задані в середовищі цього процесу
npm test

# Лише публічні тести у трьох браузерах — авторизаційні проєкти не вибрані
npm test -- --project=chromium --project=firefox --project=webkit

# Лише перевірки, які використовують збережений авторизований стан
npm test -- --project=authenticated-chromium

# Окремий позитивний тест входу (сам виконує login у чистому Chromium-контексті)
npm test -- --project=chromium --grep AUTH-002

# Публічні проєкти, навіть коли credentials задані; не запускати позитивний тест входу
npm test -- --project=chromium --project=firefox --project=webkit --grep-invert AUTH-002
```

`AUTH-002` — це перевірка самого процесу входу: вона відкриває чисту сторінку входу, вводить облікові дані та перевіряє доступ до профілю. Вона виконується в Chromium звичайного проєкту. Окремо `auth-setup` виконує вхід і зберігає стан для `authenticated-chromium`. Тому повний запуск із credentials включає і перевірку входу `AUTH-002`, і перевірку повторного використання авторизованого стану.

### Локальний запуск із credentials

Передай обидві змінні в середовище процесу `npm test` за допомогою погодженого менеджера секретів або безпечного механізму своєї оболонки. Не вставляй реальні значення в команду, README, код чи чат; не зберігай їх у репозиторії. Dotenv-завантаження вимкнене, тому саме створення `.env` не передає ці змінні тестам.

### Запуск у GitHub Actions

У репозиторії GitHub створи два **Repository secrets** через **Settings → Secrets and variables → Actions → New repository secret**:

1. `APP_EMAIL` — email тестового користувача.
2. `APP_PASSWORD` — пароль цього користувача.

Workflow передає secrets тестовому процесу й у Docker лише для окремого кроку авторизованих тестів. Він запускає цей крок на `push` або ручному `workflow_dispatch` для гілок `main`/`master`. Основний запуск публічних тестів іде окремо без credentials. Для `pull_request` (зокрема з fork) секрети не передаються й авторизований крок не запускається. Якщо обидва secrets відсутні, крок авторизованих тестів пропускається; якщо налаштований лише один — workflow завершується помилкою.

Підготовчий тест зберігає `storageState` у `playwright/.auth/user.json`. Цей файл містить авторизований стан і є секретом: Git ігнорує його, він виключений із Docker build context, його не можна поширювати чи додавати до звітів/artifacts. CI зберігає звіти/результати авторизованого запуску в окремих підкаталогах і не завантажує сам `storageState`. Після локального запуску видали файл, коли він більше не потрібен:

```bash
rm -f playwright/.auth/user.json
```

Після запуску тестів HTML-звіт можна відкрити так:

```bash
npx playwright show-report
```

Playwright налаштований на Chromium, Firefox і WebKit. Звіт створюється HTML reporter-ом, а trace збирається під час першого повторного запуску тесту.

## Опційно: Playwright CLI

У репозиторії також є додатковий skill `playwright-cli` для Claude Code: інструкції з автоматизації браузера містяться в `.claude/skills/playwright-cli/SKILL.md`, а тематичні довідники — поруч у `references/`. CLI — окремий інструмент від `@playwright/test`; він не потрібен для запуску тестів, перевірки типів чи CI.

Встанови CLI глобально та ініціалізуй підтримку браузера й skills командами:

```bash
npm install -g @playwright/cli@latest
playwright-cli install
playwright-cli install --skills
```

CLI зберігає дані браузерних сесій у `.playwright-cli/`, цей каталог ігнорується Git. Вважай snapshots, traces, скриншоти, відео й збережений стан браузера потенційно чутливими даними: перевіряй їх перед поширенням і не додавай credentials чи авторизований стан до репозиторію.

## Налаштування середовища

`.env.example` містить приклад назв змінних і placeholder-значення. За потреби його можна скопіювати для локального налаштування:

```bash
cp .env.example .env
```

Заміни placeholder-и власними локальними значеннями, але не додавай `.env` до Git і не публікуй його вміст. `.gitignore` ігнорує локальні `.env`-файли, залишаючи `.env.example` доступним.

**Важливо:** dotenv-завантаження вимкнене. Саме копіювання `.env` не завантажить змінні автоматично в тестовий процес; передавай їх через середовище процесу або CI. `FUNTIME_BASE_URL` необов'язкова й за замовчуванням дорівнює `https://funtime.com.ua`; задане значення має бути HTTP(S)-origin без шляху. Не виводь секрети в логи, звіти чи artifacts.

## Структура

```text
src/
  api/          # місце для повторно використовуваного API-коду
  components/   # повторно використовувані UI-компоненти
  config/       # конфігурація фреймворку
  data/         # спільні дані й моделі
  models/       # спільні TypeScript-моделі
  pages/        # Page Objects
  utils/        # наявні утиліти

tests/
  fixtures.ts   # типізовані test-scoped fixtures за потреби
  api/          # API-тести
  db/           # тести бази даних
  e2e/          # end-to-end сценарії
  integration/  # інтеграційні тести
  testdata/     # статичні дані для тестів
  visual/       # візуальні перевірки
```

Повторно використовуваний код розміщуй у `src/`, а специфічні для тестів сценарії, fixtures і файли — у `tests/`. Спільні типізовані fixtures розміщуються в `tests/fixtures.ts` (зараз там є fixture для `CatalogPage`). Авторизація налаштовується на рівні Playwright-проєкту через `storageState`, а не через custom auth fixture. Частина каталогів є заготовками для розвитку інфраструктури; їхня наявність не означає, що відповідний тип інтеграції вже налаштований.

У `src/utils/` зараз є утиліти для генерації тестових даних, читання JSON та змінних середовища, MySQL-запитів, очікувань UI, дат і завантаження файлів. Підключення до БД потребує доступної тестової бази й коректних runtime-змінних; наявність клієнта сама по собі цього не забезпечує.

## CI

GitHub Actions workflow у `.github/workflows/playwright.yml` запускається на push і pull request до `main` або `master`. Він встановлює залежності та браузери, виконує `npx playwright test` і завантажує `playwright-report/` як artifact. У CI Playwright використовує два retries та одного worker-а.
